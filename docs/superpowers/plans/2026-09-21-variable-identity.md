# Variable Identity Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A tracked variable has ONE name everywhere — the name it has in the result file — and a separate, recorded *expression* that is only ever a label. For a variable of the Modelica `UnitTests` component that name is `<instance>.x[i]` (`unitTests.x[3]`); the text parsed from `x={...}` (`pipe.T[1]`, `cat(1,y,y1)[2]`) becomes `expression`: stored beside the name in the reference JSON, shown as the display label on both tiers, and soft-checked on compare. The two renaming layers that exist today — `backends/common/result_variables.py::extract_variables` (name := expression text, or `expr[i]`, or `x[i]`) and `comparison/comparator.py::variable_label` (a `cat(`/newline name := `x[N]` for scoring and display only) — are deleted, and with them the reason ~70 TRANSFORM tests have no editable criteria tree in `dstf author`.

**Owner rulings this plan builds on (2026-09-21; not reopened):** "respect the source of the data"; no bespoke label→name mapping; the identity is `unitTests.x[i]` for EVERY UnitTests variable, not only the ones whose expression is awkward; the expression is recorded and is a soft warning check; the stored baselines change, so a migration utility is the coordination with TRANSFORM.

**Why (measured 2026-09-21, read-only, TRANSFORM Dymola/linux, 331 baselines / 877 variables):** stored names are 385 plain, 60 expression text, 178 `x[i]` (the model's own array `x`, via `x=x`), 210 holding a newline (plain names whose `.mo` source wrapped a line: `heatTransfer.alphas[\n        1, 1]` — the parser keeps the whitespace), 44 `cat(`. Discovery: 313 `unit_tests` + 18 `both`; expression shapes 184 one-per-variable, 147 one-expression-many-variables, 0 otherwise; the 18 `both` tests carry no spec variable patterns. All 321 `UnitTests` instances in TRANSFORM are named `unitTests`; `mo_parser` accepts any instance name while four backend sites hardcode `unitTests.x[`. TRANSFORM's `test_spec.json`: 18 entries, no `metrics`, no `plots`, ONE `variable_overrides` key — `pipe.mediums[1].p` on `…MSLFluid.HeatingSystem`, which is that test's `x[3]` expression and must become `unitTests.x[3]`.

**Architecture — five moves.**
1. **Discovery knows the instance and cleans the text.** `mo_parser` captures the instance name and collapses whitespace inside parsed expressions (any run of whitespace → one space; none after `[`/`(` or before `]`/`)`/`,`). `RecognizerResult` and `TestModel` gain `unit_tests_instance: str = "unitTests"`; `json_recognizer` threads `ComponentMatch.instance_name` into it.
2. **One function names UnitTests variables.** New `discovery/unit_tests.py::unit_test_variables(test) -> list[UnitTestVariable(name, expression)]`, length `n_vars`: `name = f"{instance}.x[{i}]"`; `expression` is `x_expressions[i-1]` when there is one per variable, `f"{x_expressions[0]}[{i}]"` when one expression covers several, else `""`. Every `f"unitTests.x[{i}]"` in `src/` is replaced by it (result_variables ×2, openmodelica backend, openmodelica persistent backend).
3. **`expression` rides beside `name`, never instead of it.** `VariableResult.expression: str = ""` and `VariableComparison.expression: str = ""`. `extract_variables` sets `name` to the result-file name and `expression` from move 2; the `seen` de-dupe is by result-file name only. The reference JSON's variable entry is `{"index", "name", "expression", "values"}` — the writer always writes `expression` (possibly `""`). Overrides, tree leaves, `plots` series, baselines, figure ids, DOM attributes and test markers are keyed by `name`. `variable_label` and every `name or f"x[{index}]"` fallback are deleted; so is every `ref_var.get("name") or ref_var.get("expression")` read (nothing has written `expression`-as-a-name since before v1.0; the key now means something else).
4. **One label rule.** `backends/types.py::display_label(name, expression) -> str` returns `expression or name`. Every human-facing string uses it; section and card TITLES also show the name, muted, when it differs from the label (`pipe.T[1]` · `unitTests.x[1]`), so two variables with one expression stay tellable apart.
5. **The expression is a soft check.** On compare, when the baseline's entry and the result's variable both carry a non-empty `expression` and they differ, the test gets a warning — `unitTests.x[2]: the baseline recorded "a.Q", this run measures "b.Q"` — through the same channel as the structural warnings (it does not fail the test). This is what makes a positional name safe.

**Seam change, and its coordination.** Reference-JSON variable names and `test_spec.json` keys that name an expression change. `dstf migrate-variable-names` (Task 5) rewrites both, dry-run by default. There is NO compatibility read: an un-migrated baseline meets the existing "reference index N holds … — treating as missing baseline" path, whose message gains one clause naming the command. The command is deleted at the v1.0 tag (say so in its module docstring).

**Not built here:** any change to pattern-tracked (spec) variables, diagnostics, companions' own files (they are the user's data, keyed by their own names); Julia / Python / FMPy naming (their variables already carry result-file names; `expression` stays `""`); the form row and the legend (next plan).

### Task 5 — `dstf migrate-variable-names`

**Files:** new `src/dstf/cli/migrate_cmds.py` (+ registration in `cli/main.py`), new `src/dstf/storage/migrate_names.py`; tests new `tests/test_migrate_variable_names.py`; then the repo's own checked-in baselines under `examples/**` migrated BY the command and committed separately.

- [ ] Behaviour. Dry-run by default, `--apply` writes (same convention as `manifest cleanup`). Walks EVERY `<reference_root>/<Backend>/<os>/` partition, primary `ref_NNNN.json` and `soft_checks/**.json`. For a file whose `model_id` discovery resolves to a test with UnitTests variables, for `i` in `1..n_vars`: the entry with `index == i` is rewritten to `name = <instance>.x[i]`, `expression = <the rule's expression>` iff `_normalize_expression(stored name)` equals that expression, or the entry is already migrated (idempotent); every other entry gains `"expression": ""` if it lacks the key. Any entry in `1..n_vars` that matches neither is reported by file, index, stored and expected text, and THAT FILE is left untouched. Files whose model discovery does not know are listed and untouched. Then `test_spec.json`: within each entry of a UnitTests test, a `comparison.variable_overrides` key, a `metrics` leaf `variable`, and a `plots` series `var` equal (normalized) to one of that test's expressions becomes the name — through the project's shared spec read-modify-write, not a hand-rolled dump; an expression that two indices share is reported and left. Output: counts per partition (files rewritten / already migrated / skipped with reasons / unknown model), spec keys rewritten; exit 1 if anything was skipped. JSON written with the store's own writer (LF, same key order as `accept` produces, `expression` after `name`).
- [ ] RED tests for each sentence above, plus: bytes of `time` / `values` / every other key unchanged (compare parsed JSON minus the two keys); a second `--apply` run rewrites nothing; dry-run writes nothing (mtime and bytes).
- [ ] Mutations: matching without normalization (a newline name is then skipped); a partially-matching file half-written; dry-run writing; spec rewrite touching a pattern-tracked key; exit 0 with skips.
- [ ] Run it (`--apply`) over `examples/modelica/ModelicaTestingLib` and any other tracked reference root; suite green; commit the data separately: `examples: baselines carry result-file names and expressions`.
